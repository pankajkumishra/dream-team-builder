# Research: Dream Team Builder — Team Compatibility Platform

**Feature**: `001-team-compatibility` | **Date**: 2026-06-17

All Technical Context unknowns resolved. No remaining `NEEDS CLARIFICATION` items.

---

## 1. Application Architecture

**Decision**: Next.js 15 monorepo with App Router, TypeScript throughout, PostgreSQL via Prisma.

**Rationale**: The spec requires a responsive web app (FR-020) with server-side validation (FR-019), structured relational data (profiles, assessments, connections), and fast API responses (SC-002). A single-language TypeScript stack reduces context switching for a small team, and Next.js Route Handlers provide a clean API boundary without premature microservice extraction.

**Alternatives considered**:
- **FastAPI + React**: Stronger ML ecosystem but adds Python/TS split and deployment complexity for MVP.
- **Supabase-only backend**: Faster bootstrap but less control over compatibility scoring logic placement.
- **Microservices**: Rejected — violates Simplicity principle at 1,000-user scale (SC-007).

---

## 2. Authentication

**Decision**: Auth.js (NextAuth v5) with email/password and OAuth providers (Google, GitHub).

**Rationale**: Spec assumes standard account-based auth with email or social login. Auth.js integrates natively with Next.js, supports session management for protected API routes, and keeps credentials out of application code.

**Alternatives considered**:
- **Clerk**: Faster UI components but adds vendor dependency and cost.
- **Custom JWT**: More implementation surface for equivalent v1 needs.

---

## 3. AI / Compatibility Analysis Strategy

**Decision**: Hybrid engine — deterministic TypeScript scoring module + LLM for natural-language explanations only.

**Rationale**:
- **Deterministic layer** computes dimension scores (work-style, goals, skills, communication), risk flags, confidence levels, and success probability. This is unit-testable (Constitution III), reproducible, and meets the <30s SLA (SC-002) without LLM latency for core math.
- **LLM layer** (OpenAI GPT-4o-mini or Azure OpenAI equivalent) generates plain-language explanations from structured scoring output (FR-010). Also powers composition recommendation narratives (FR-012) and work-style profile summaries (US1 scenario 3).

**Scoring approach (v1)**:
- **Work-style alignment**: Cosine similarity on normalized assessment trait vectors (6–8 dimensions derived from questionnaire).
- **Goal alignment**: Weighted overlap on project type, timeline, commitment level; flag direct conflicts (e.g., exit vs. research) as high-risk.
- **Skill complementarity**: Coverage matrix against project-relevant skill categories; flag redundancy (≥2 members same primary skill) and gaps (zero coverage in critical category).
- **Communication fit**: Derived from assessment dimensions (directness, async preference, feedback style).
- **Success probability**: Weighted composite (0–100) with confidence penalty when assessment skipped or profile incomplete (FR-017).
- **Stale results**: Hash profile version fields; mark analyses outdated when any member profile changes materially (FR-018).

**Alternatives considered**:
- **LLM-only scoring**: Non-deterministic, harder to test, slower, opaque — violates FR-010 intent and Constitution III.
- **Custom ML model training**: Out of scope for v1; insufficient labeled team-outcome data.
- **Third-party personality APIs**: Spec assumes in-platform questionnaire (Assumptions).

## 4. Work-Style Assessment Design

**Decision**: Platform-native questionnaire (~20–25 items) mapping to 6–8 work-style dimensions, completed in-profile.

**Dimensions (v1)**:
1. Collaboration preference (independent ↔ highly collaborative)
2. Pace / urgency tolerance
3. Risk tolerance
4. Communication directness
5. Structure preference (planned ↔ adaptive)
6. Conflict handling style
7. Commitment intensity
8. Feedback receptivity

**Rationale**: Standardized in-platform assessment per spec assumptions. Items use Likert scales (1–5). Trait summary generated by LLM from dimension scores for plain-language output (US1).

**Alternatives considered**:
- **Big Five / DISC imports**: Clinical instruments out of scope; licensing complexity.
- **Free-text only**: Harder to score consistently; poor for deterministic analysis.

## 5. Database & Data Modeling

**Decision**: PostgreSQL 16 with Prisma ORM.

**Rationale**: Relational model fits User → Profile → Assessment → TeamAnalysis → Connection entity graph. JSON columns for flexible skill lists and assessment responses. Supports visibility flags, connection state machines, and stale-analysis tracking.

**Alternatives considered**:
- **MongoDB**: Weaker relational integrity for connection workflows and duplicate-profile prevention.
- **SQLite**: Insufficient for concurrent multi-user discovery at scale target.

---

## 6. Discovery & Matching (P4)

**Decision**: SQL-based filtering and ranking for MVP; defer vector/semantic search.

**Ranking factors**:
- Compatibility preview score (lightweight pairwise scorer)
- Skill complementarity with searcher's stated needs
- Goal/project-type overlap
- Visibility opt-in filter (FR-015)

**Rationale**: At 1,000 profiles (SC-007), indexed SQL queries are sufficient. Semantic search (pgvector) adds complexity without proven v1 need.

**Alternatives considered**:
- **pgvector + embeddings**: Better for fuzzy skill matching; deferred to post-MVP.
- **Elasticsearch**: Over-engineered for initial scale.

---

## 7. UI Framework & Accessibility

**Decision**: Tailwind CSS + shadcn/ui (Radix primitives).

**Rationale**: Radix provides accessible focus management, ARIA patterns, and keyboard navigation for wizard steps, modals, and report cards. Tailwind enables responsive layouts for desktop/mobile (FR-020, Constitution I).

**Alternatives considered**:
- **Material UI**: Heavier bundle; less customization for brand.
- **Chakra UI**: Comparable; shadcn/ui preferred for copy-paste ownership of components.

---

## 8. Testing Strategy

**Decision**: Vitest (unit + integration) + Playwright (E2E).

**Test priorities**:
| Layer | Target |
|-------|--------|
| Unit | `CompatibilityScorer`, `RiskDetector`, `ConfidenceCalculator`, Zod schemas |
| Integration | API route handlers with test database |
| E2E | Profile wizard completion, 2-person analysis report, discovery opt-out |

**Rationale**: Constitution III requires automated tests for business logic and critical flows. Scoring logic is the highest-value test target.

---

## 9. Deployment & Secrets

**Decision**: Vercel (application) + managed PostgreSQL (Neon or Supabase Postgres); environment variables for `DATABASE_URL`, `AUTH_SECRET`, `OPENAI_API_KEY`.

**Rationale**: HTTPS by default (Constitution Security). No secrets in repo. Single deploy target for MVP simplicity.

**Alternatives considered**:
- **Docker + VPS**: More ops overhead for v1.
- **Azure Static Web Apps + Azure PostgreSQL + Azure OpenAI**: Valid if team is Azure-aligned; equivalent architecture.

---

## 10. API Versioning

**Decision**: URL prefix `/api/v1/` for all endpoints.

**Rationale**: Constitution IV requires explicit, versioned API contracts. v1 prefix allows breaking changes in future versions without silent client breakage.

**Alternatives considered**:
- **Unversioned `/api/`**: Acceptable only for pre-release; versioning from day one is low cost.
